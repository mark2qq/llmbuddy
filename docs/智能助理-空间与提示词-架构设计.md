# 智能助理 · 空间与提示词 · 架构设计（v1.0.11）

> 配套实现：`core/assistant/store.py`（存储）、`core/assistant/agent.py`（业务）、
> `routers/assistant.py`（HTTP）、`client/ui/pages/assistant_page.py`（左栏导航 + 底栏）。
> 交互与结构对齐 WorkBuddy：左栏「任务 (N) / 空间 (N)」两区，底栏「📝 提示词 / ✨」。

---

## 1. 背景与关键约束

用户原始约束（不可偏离）：

1. **空间功能**：创建、命名、切换、管理多个相互独立的空间，空间之间数据隔离。
2. **提示词功能**：创建、编辑、存储、复用提示词，跨场景快速调用。
3. **关键 bug 修复**：先前在空间内创建任务会**覆盖**之前的任务。一个空间必须能同时承载
   多个相互独立的任务，各任务互不覆盖、可分别查看与切换。
4. 布局与操作方式贴近 WorkBuddy，功能完整、结构清晰、交互一致。

「覆盖」错觉的根因：旧导航只渲染每个工作区**最新一条**任务，用户切到空间后看起来像
「只剩刚建的」。修复方式不是迁移 session 文件，而是让空间行**可展开**显示其全部任务，
且创建新任务只新增一条、绝不改写既有任务（`new_session` 始终 append，主键 `id` 唯一）。

## 2. 空间（Spaces）

### 2.1 数据模型

空间 = 具名、可切换的**工作区目录**，不做 session 文件迁移，任务通过 `workspace` 路径归属。

- 注册表：`spaces/registry.json`（位于 `%LOCALAPPDATA%\llmBuddy\assistant`）
  - 字段：`name`、`order`、`current`、`pinned`（布尔，置顶）
  - `current` 至多一个为 `true`，作为默认活跃空间
- 任务归属：每条 session 自带 `workspace` 字段；空间即「某个 `workspace` 目录」的具名视图。
- 隔离性：不同 `workspace` 目录天然物理隔离；删除空间只清注册表与排序，**不删**目录下任务。

### 2.2 空间列表（`store.space_list`）

返回结构（导航与 HTTP 共用）：

| 字段 | 含义 |
|------|------|
| `path` | 工作区目录绝对路径（归一化） |
| `name` | 空间显示名 |
| `current` | 是否当前活跃 |
| `order` | 排序权重 |
| `pinned` | 是否置顶 |
| `count` | 该空间任务数 |
| `tasks` | **全部**任务列表（按 `updated_at` 倒序，不再只取最新一条） |
| `exists` | 目录是否仍存在（缺失目录标警示，不崩溃） |

合并来源：① 注册表里登记过的空间（含「已登记但暂未建任务」的空空间）；② 有任务但未
登记的空间（自动补登记）。空空间也出现在列表里，避免「建了空间却看不到」。

### 2.3 导航渲染（异步 + 可展开）

```
refresh()
  └─ _apply_sessions() → _fill_spaces()
                           └─ Worker(self._assist.spaces)   # 异步拉 GET /spaces
                              └─ _apply_spaces(spaces)
                                 └─ self._nav_spaces = spaces
                                 └─ _rebuild_nav_tasks()      # 渲染左栏两区
```

- 空间行点击（`_on_space_header`）：切换展开/收起；展开时 `activate_space` 设为当前空间，
  并自动打开该空间**最新**一条任务（`_open_task`）。
- 展开后列出该空间 `tasks` 全部条目（每条约 62px 行高，不裁文字）。
- 收起态：空间行只显示 `名称 (N)`，点行即展开——不再「看起来覆盖了旧任务」。

### 2.3.1 两区不重复（用户截图反馈）

「任务」区**只列系统默认工作区**的任务（`_default_ws()`，后端 `state.default_workspace`），
其他空间的任务只在下方「空间」区出现。跨空间全列会让同一个任务在左栏出现两行
（任务区一条 + 空间展开区一条），用户会误以为「建了 2 个新任务」。

- 空态文案：「默认工作区还没有任务，点上方 + 新建（其他空间的任务见下方）」。
- 「空间内建任务像覆盖」由空间可展开列**全部**任务解决，不靠任务区兜底——两个问题分开治。

### 2.4 空间 HTTP 端点（`routers/assistant.py`）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/spaces` | 新建空间（建目录 + 登记注册表） |
| PATCH | `/spaces/{key:path}` | 重命名 / 调整排序 / 置顶 |
| DELETE | `/spaces/{key:path}` | 注销（清登记，保留任务目录） |
| POST | `/spaces/{key:path}/activate` | 设为当前空间 |
| GET | `/spaces` | 列出全部空间（含 `tasks`/`count`/`exists`） |

### 2.5 多任务并行（运行态隔离）

任务运行态在 `TaskRun` 里、不在页面上（`_cur_sid` 事件上下文代理）。同一空间内多个任务
可同时运行，各自 `_stream/_busy/_bubble/_thinking/_proc/_approvals` 互不串台——这与
空间修复同源：空间的「任务」是一等集合，页面只负责**渲染集合**，不持有单例运行态。

## 3. 提示词（Prompts）

### 3.1 数据模型

全局可复用提示词库（**不**按空间隔离，跨空间/跨会话都能调）：

- 存储目录：`prompts/`（位于 `%LOCALAPPDATA%\llmBuddy\assistant`）
- 单条文件：`{id}.json`，`id = "p" + uuid4().hex[:12]`（12 位足够本地唯一、短易读）
- 字段：`id`、`title`、`content`、`created_at`、`updated_at`、`tags`（可选）

### 3.2 存储函数（`store.py`）

| 函数 | 说明 |
|------|------|
| `save_prompt(p)` | 新建或更新（按 `id` upsert，幂等） |
| `load_prompt(pid)` | 读单条 |
| `list_prompts()` | 列出全部（按 `updated_at` 倒序） |
| `delete_prompt(pid)` | 删除单条 |

### 3.3 UI 入口（按用户要求：底栏只留 ✨）

| 入口 | 对象 | 行为 |
|------|------|------|
| 输入框右键「插入提示词…」 | `PasteImageEdit.prompt_requested` → `_open_prompt_picker` | 打开 `_PromptPicker`：从库选一条插入输入框；可跳转「管理提示词库」。**底栏不再放「📝 提示词」按钮**（截图反馈底栏太挤），功能入口改为右键，不占宽度 |
| 底栏 `✨`（右组首位，**仅输入框有内容时出现**） | `GuideBtn` `_enhance_btn` | 把当前输入框文字交给模型改写为结构化「增强版提示词」（`/enhance` 专用端点、临时流、不改写原文）。显隐见 `_sync_enhance_visible` |

- 插入规则（`_insert_prompt`）：输入框非空则换行追加（`\n\n`），空则直接写入；光标移到末尾。
- 空输入点 ✨ 给中文提示「输入框是空的，先写点内容再优化吧」，不发起请求。
- 提示词管理对话框 `_PromptManagerDialog`：新建 / 编辑 / 删除 / 复用。

### 3.4 提示词 HTTP 端点（`routers/assistant.py`）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/prompts` | 列出全部 |
| POST | `/prompts` | 新建（`title`+`content`） |
| GET | `/prompts/{pid}` | 读单条 |
| PATCH | `/prompts/{pid}` | 更新（幂等） |
| DELETE | `/prompts/{pid}` | 删除 |

空 `title`/`content` 由后端校验拒绝（测试 `test_http_prompt_rejects_empty`）。

### 3.5 增强提示词 ✨（2026-10-27 重做为内联流式）

点 ✨ 就是**一次纯 LLM 改写**：不弹窗、不建会话、不落库，结果直接在输入框里流式长出来
（对齐 WorkBuddy）。

**为什么重做**——用户反馈「点了没反应」，旧版是四个问题叠加：

| 旧实现 | 症状 | 现在 |
|---|---|---|
| 借道 `POST /chat` + 临时会话 | 要过 agent 主循环与阶段闸门，首字延迟高，左栏还闪过一条任务 | 专用 `POST /enhance`，只做 `provider.chat → 转发 delta` |
| `provider` / `model` 传空串 | 后端回落到配置默认模型，与界面所选不是同一个 → 像没动静 | 显式带 `_active_provider` / `_active_model` |
| `appendPlainText(每个 delta)` | Qt 的 append 语义是「新段落」→ 逐 token 变成「一\n个\n字\n一\n行」 | 累积后 `setPlainText` 整体回填 |
| 只处理 `delta` / `replace` | 思考阶段的 `reasoning` 全丢弃 → 几十秒界面空白 | 状态行显示「模型思考中…（已 N 字）」，正文一到就进输入框 |

**模板**：单一来源 `core/assistant/enhance.py:SYSTEM_PROMPT`（客户端不再保存副本）。六条改写要求
不变，但**去掉三段式的「主要改动 / 待确认」**——结果直接回填输入框，多两个段落既污染输入框，
又让本地模型多花一倍时间。另加三条硬约束（都是实测踩到的坑）：

- **输出语言必须与原文一致**：原文「画一副江南水乡的图」曾被整段改写成英文 SD prompt；
- 篇幅 ≤500 字；
- 不输出思考过程 / 分析步骤。

**输出预算 `MAX_OUTPUT_TOKENS = 16384`**：思考型模型（qwen3 / Xing4 关不掉思考）先把预算烧在
reasoning 上。实测 Xing4.0-29B 单次约 830 字思考 + 50~300 字正文；若给 4096 会被吃光 →
`chat()` 判 content 为空 → 自动放大重试 → **再做一次完整调用**，耗时从 16s / 25s 涨到 185s。
给足后恒为单次调用。

**交互细节**：

| 场景 | 行为 |
|---|---|
| 空输入 | `QMessageBox.information` 提示，不发请求 |
| 增强中 | 输入框只读、placeholder 改「正在增强…」、✨ 变 ⏹、发送按钮暂禁 |
| 思考中 | 状态行累计字数 + 「点 ⏹ 可取消」；思考内容**不写**输入框 |
| 完成 | `_extract_enhanced_prompt()` 兜底剥标题/围栏 → 整段写入；状态行「已增强（12 → 46 字）」 |
| 再点 ⏹ | `stream.cancel()` + 原文还原 |
| 失败 / 提前关流 | 一律还原原文；只有已收到内容才当成功，绝不把输入框留空 |

状态字段（`_enhancing` / `_enhance_origin` / `_enhance_acc` / `_enhance_think` / `_enhance_stream`）
是**输入框级**状态，不属于任何任务，所以挂在页面上而不是 `TaskRun` 里。

| 元素 | 位置 | 职责 |
|---|---|---|
| `SYSTEM_PROMPT` / `build_messages()` / `clip()` / `is_blank()` | `core/assistant/enhance.py` | 模板与消息构造（单一来源） |
| `POST /api/v1/assistant/enhance` | `routers/assistant.py` | SSE：`start` / `reasoning` / `delta` / `reset` / `done` / `error` |
| `AssistantStream(path=...)` | `client/core/assistant_client.py` | 同一套 SSE 读取，端点可换（默认仍是 `/chat`） |
| `_enhance_prompt()` / `_on_enhance_event()` / `_finish_enhance()` / `_cancel_enhance()` | `client/ui/pages/assistant_page.py` | 内联流式回填、取消、还原 |

## 4. 底栏布局与宽度门禁

真实窗口最小宽 **1000**、左栏 **200** → 右栏最窄约 **770**。所有底栏按钮必须**始终可见**，
不做宽度自适应隐藏。

底栏最终形态（用户按截图指定，1.0.12 再调）：

```
[+] [工作区] [自动] [技能] [工具] [MCP] [技能chip…] ─stretch─ [✨] [◌运行] [模型▾] [■] [⚡] [↑]
◐ 上下文 33% · 2.6k/8.0k            内容由 AI 生成，请核实重要信息
└──── 输入框下方信息行（1.0.12 把上下文占用挪到这里）────┘
```

- **`📝 提示词` 已移除**（用户要求收紧底栏）：提示词库入口改到**输入框右键 →「插入提示词…」**
  （`PasteImageEdit.prompt_requested` → `_open_prompt_picker`），功能不失联、不占底栏宽度。
- **`✨ 增强提示词` 留在 `[MCP]` 右侧的右组首位**，并改为**按内容显隐**：
  输入框 trim 后为空 → 隐藏；有内容 → 出现；增强进行中（此时按钮是 ⏹）恒显示。
  实现：`_input.textChanged` → `_sync_enhance_visible()`。
- **上下文占用移出底栏**（用户原话「把上下文信息区域移动到对话框下方」）：`ContextMeter`
  圆环 + `_ctx_meta` 文字标签放在输入框下方的信息行左端，右侧仍是合规提示；
  该行可用宽 ~940，不受底栏门禁约束，所以能带文字（`上下文 33% · 2.6k/8.0k`），
  无数据时圆环与文字一起隐藏。同步入口：`_apply_context()` → `_sync_ctx_meta()`。
- **运行指示放大**：原 `◐` 文本字符（`#BusyDot`，13px / 16px 槽位）换成自绘圆弧控件
  `ui/widgets/busy_spinner.py::BusySpin`（24×24、线宽 2.2、40ms 转 24°≈600ms 一圈、
  颜色跟随 palette，`start()` / `stop()` 同时管可见性）。
- 门禁常量：`AssistantPage.BAR_BUDGET_W = 720`（= 770 - 50 边距/抖动/缓冲）。
- 实测（1.0.12，QT_SCALE_FACTOR=2 抓图核对底栏 `sizeHint`）：空闲+✨ **384px** /
  忙碌（+加载环+停止+引导）**470px** / 空闲无内容（✨ 隐藏）**356px**，均 ≤ 720；
  `_chips_width_over_budget` 的 `base` 取最挤值 **470**。
- 挂载技能 chip：≥3 个（或超预算）时 `_reparent_skill_chips` 把 chip 容器折到输入框上方
  独立一行（规则④），底栏恒不溢出。
- 单一来源：`BAR_BUDGET_W` 由页面类定义、测试从类导入，不在测试里硬编码字面量。

## 6. 工具循环熔断与结果展示（1.0.11 同版修复）

用户截图暴露的问题：助理反复调 `skill_list`（「读取技能列表」）空转到上百步，
且「深度思考」与工具结果内容都不显示。

### 6.1 根因
- `DEFAULT_MAX_TOOL_ROUNDS = 0`（不限制轮次），主循环没有任何「原地打转」检测，
  只靠 900s 墙钟 + 手动停止 —— 模型反复调同一工具时可空转上百步。
- 前端 `ProcessLine.set_result(pos, ok)` 只记成功标志，**丢弃 `tool_result.content`**，
  所以技能清单只显示一行「读取技能列表」，看不到内容。
- 空/纯空白 `reasoning` 也会懒建 `ThinkingBlock`，循环里就铺出一堆空的「深度思考」。

### 6.2 修复
**后端（`core/assistant/agent.py`）—— 重复调用熔断**（保留「不设轮次上限」以支持合法
多步任务，改为止步于「无进展」）：
- 每轮取「本轮全部调用的 (name, 规范化 args)」做签名 `round_sig`。
- 判据①：连续 `LOOP_REPEAT_LIMIT=3` 轮签名完全相同 → 立即中止（用户截图场景）。
- 判据②：最近 `LOOP_WINDOW=10` 轮内同签名出现 `LOOP_ALT_LIMIT=6` 次 → 中止（抓 A/B 交替）。
- 中止时下发明确 `error`：「检测到工具「X」被以完全相同的参数重复调用 N 次…已中止」，
  并提示可直接在左侧「技能」面板查看清单。

**前端（`client/ui/widgets/assistant_cards.py` + `assistant_page.py`）—— 完整展示 + 合并**：
- `ProcessLine.set_result(pos, ok, content)` 新增结果正文；`_refresh` 在展开体里渲染
  结果（超 4000 字截断、可选中复制）——技能清单/文件内容都能看到。
- 同签名连续调用不再新起步骤/新起进程行，改为该步 `repeat += 1`，显示「读取技能列表 ×N」。
- `reasoning` 事件空文本不建块；`ThinkingBlock.set_text("")` 已有隐藏逻辑 → 不再留空壳。

### 6.3 测试
- 后端：`test_turn_aborts_on_repeated_identical_tool_call`、
  `test_turn_distinct_calls_do_not_trip_loop_guard`（不误伤合法多步）。
- 客户端：`test_tool_result_content_is_shown_in_process_line`、
  `test_repeated_identical_tool_call_merges_not_piles`。

## 7. 空任务（「新任务」幽灵）治理 —— 2026-10-27 用户反馈「一直有个新任务删不掉」

现象：某个空间下长期挂着一条「新任务 / 0 条消息」，右键删除后立刻又出现一条同样的，
像永远删不掉。

### 7.1 根因（三个机制互相加固）

| # | 机制 | 后果 |
|---|---|---|
| ① | `_on_session_deleted` 删的若是**当前任务**，会 `_new_session(silent=True)`「兜底新建」 | 删一个 → 后端立刻在同一工作区补一条 0 条消息任务 → 看起来没删掉 |
| ② | `refresh()` 首次进入时若没有可复用的空任务，也 `_new_session(silent=True)` | **每启动一次就多一条**空任务，成为 ① 的素材 |
| ③ | `_apply_sessions` / `space_list` 对「0 条消息」不做过滤，且「是当前任务就保留」 | 空任务一直显示在左栏与空间展开区；而它又会被启动逻辑继续复用为当前任务 |

`_sweep_empty_sessions`（清理空任务）当时还把当前任务**排除在外**，于是「当前那个空任务」
连一键清理都躲得过去。

### 7.2 修复

- **删除当前任务不再自动新建**（`_on_session_deleted`）：
  先把 `was_current` 记下来（`_dispose_run` 会清空 `_active_sid`，之后再比较永远不相等）；
  还有别的任务 → 切到最近一条；一条不剩 → `_enter_draft()` 进**空白草稿态**（`sid=""`，不落盘）。
  草稿态发送时由 `_on_send_clicked` 先 `new_session` 再发，所以「没有任何任务」是合法状态。
- **启动不再凭空建任务**（`refresh`）：没有可复用的空任务就进草稿态，任务只由用户点「+」
  或首次发消息产生。已有草稿容器时不重复清空（`refresh` 会多次进来）。
- **左栏不显示僵尸空任务**：`_apply_spaces` 过滤「0 条消息且非当前任务且未在跑」的条目，
  并按过滤后的可见数重算 `count`（后端 `space_list` 是按 workspace 全量分组，会把空任务一起下发）。
- **「清理空任务」包含当前任务**（`_sweep_empty_sessions`）：先把当前切到草稿再删，
  避免删除回调把「当前任务」判成还在又切一条回来。

### 7.3 已发生的存量数据

用户机器上已有的空任务文件需清理一次（`%LOCALAPPDATA%\llmBuddy\assistant\sessions\*.json`，
`message_count == 0`）。本次已把 `se92d8a73eec8`（newspace / 0 条 / 20:51）备份后删除，
备份在 `sessions/_trash/`。界面侧的手工步骤：**先点开同空间另一条任务把它变成「非当前」，
再右键删除**（旧版代码只在删「当前任务」时才重建）。

## 8. 风险与遗留

- 空间删除是「注销登记」语义，不删任务文件；若用户期望彻底删除目录，需另行确认（当前按
  WorkBuddy「空间只是命名视图」的口径，避免误删数据）。
- 提示词库是全局的，不随空间切换隔离；若后续需要「每空间私有提示词」，在 `prompts/` 下
  按 `workspace` 加子目录即可，存储函数与端点已预留扩展位。
- 版本号：客户端 `APP_VERSION`、后端 `state()["version"]`、安装包 `MyAppVersion` 三处统一为
  `1.0.12`。
