# 智能助理 · 引导会话（消息排队）增量 PRD

> 版本：v1（增量） · 作者：许清楚（产品经理） · 日期：2026-08-08
> 关联文档：`docs/智能助理.md`（既有功能基线）

## 1. 项目信息

- **Language**：中文
- **Programming Language**：Python —— PySide6 客户端 + FastAPI 后端（沿用现有架构，不引入 Web 技术栈）
- **Project Name**：`guided_conversation_queue`
- **原始需求复述**：「@image#1 添加引导会话功能，请详细分析 workbuddy 的引导功能 参照实现」
- **需求基线**：WorkBuddy「引导会话」调研结论（主理人已确认）——执行期间发消息不打断当前轮，进入输入框上方队列，本轮结束按序消费；另有「立即发出（引导）」档位：消息马上登记进对话流、引导后续方向，但同样不中断当前输出；队列消息可编辑/删除/排序，进入对话流后只读（显示发送时间、可复制、不可撤回）。

## 2. 产品定义

### 2.1 产品目标（一句话）

让用户在大模型执行期间也能持续输入——消息以「排队 / 引导」两种语义有序接入当前会话：**不打断当前生成、不丢失、队列内可改、进了对话流只读**。

### 2.2 本次增量范围

- 只做「引导会话 / 消息排队」：执行中插话排队、队列编辑/删除/排序、引导发送、跨轮次自动消费。
- WorkBuddy 其它特性（引用文本、添加到对话、划词问答等）**不做**，列入 P2 待办池。
- 不改动 `agent.py` 的单轮工具循环、审批、并行工具执行逻辑。

### 2.3 用户故事

1. **执行中插话排队**：作为用户，我在助理执行时想补发下一件事而不打断当前输出，以便思路连续、不用干等。—— 忙碌态 Enter / ↑ 入队。
2. **排队消息可改**：作为用户，我想在消息发出前编辑 / 删除 / 调整已排队消息，以便改主意零成本。—— 队列行内 ✎ / ✕ / ↑↓。
3. **立即引导发送**：作为用户，我想把某条消息立即引导发出（登记进对话流但不打断当前生成），以便及时纠正方向并留痕。—— ⚡ 按钮 / Shift+Enter。
4. **进了对话流只读**：作为用户，我想看到引导发出的消息带发送时间且之后不可再改，以便分清「队列里还能改」与「已发出只能看」。—— guided 气泡 + 时间戳。
5. **跨轮次自动消费**：作为用户，我希望本轮结束后排队消息按序自动消费、继续生成，以便不用手动一条条重发。—— 自动消费 + `dequeued` 状态可见。

## 3. 需求池（P0 / P1 / P2）

### P0（Must have）

| # | 需求 | 验收标准 |
|---|------|----------|
| P0-1 | 执行中发消息进队列、不打断 | 忙碌态（`_busy=True`）输入非空消息按 Enter 或点 ↑：消息进入输入框上方队列；当前 SSE 流持续输出，无中断、无重连、无界面跳变；后端返回入队确认，客户端队列与后端快照一致。**修复现状**：`_on_send_clicked` 当前 busy 直接 return（消息被丢弃） |
| P0-2 | 本轮结束自动按序消费并继续生成 | 当前轮 `done` 后，后端按 FIFO 自动出队下一会话消息，在**同一条 SSE 连接**内继续 `start_turn`；客户端忙碌态不中断（`end` 事件仅在队列耗尽/暂停时发出）；`dequeued` 后对话流出现对应用户消息与新答复；队列为空时流正常 `[DONE]` 关闭 |

| P0-4 | 立即引导发送（进对话流但不打断） | 忙碌态点 ⚡ 或 Shift+Enter：消息**立即**以用户气泡进入对话流（含发送时间），当前输出不中断；该消息此后不可编辑/删除；后端发 `guided` 事件登记，按 FIFO 参与后续轮次 |

## 4. UI 设计稿

### 4.1 整体结构（文字 + 结构图）

```
┌─ 对话区（ChatScroll，内容列宽 ≤940） ─────────────┐
│ …历史消息…                                        │
├─ 队列容器（新增，仅忙碌且队列非空时显示）──────────┤
│ 排队中（2）· 本轮结束后按序发送          [全部清除] │
│ ① 把 README 翻译成英文         [✎][↑][↓][✕]       │
│ ② 顺便更新截图                 [✎][↑][↓][✕]       │
│ （暂停态：头部显示「已暂停 · 继续」按钮）           │
├─ 输入区（Composer，现状微调）─────────────────────┤
│ 输入框（placeholder 随忙碌态切换）                 │
│ [+] [工作区] [⊘ 只读自动] [技能] ◐ [模型 ▾] [⚡][↑][■] │
└───────────────────────────────────────────────────┘
```

- **队列容器位置**：footer 的 `inner` 布局中，插在 `_build_composer()` 正上方（与 status 提示同行区域之上），与输入框同宽居中。
- **行内元素**：序号、消息文本（单行省略，hover tooltip 显示全文）、编辑 ✎ / 上移 ↑ / 下移 ↓ / 删除 ✕。
- **三种操作入口**：① 行内按钮（编辑/删除/排序）；② 容器头部「全部清除」；③ 输入框本身（Enter 入队 / Shift+Enter 引导）——第三条即「发送入口」。

### 4.2 忙碌时发送区状态机（推荐方案）

| 状态 | ↑ 按钮 | ⚡ 按钮（新增） | ■ 停止 | 键盘 |
|------|--------|----------------|--------|------|
| 空闲（现状不变） | 发送 | 隐藏 | 隐藏 | Enter 发送；Shift+Enter 换行 |
| 忙碌 | **排队入队** | **引导发送** | 显示 | Enter 排队；Shift+Enter 引导 |

- ↑（原位，忙碌时语义变为排队）：tooltip「排队发送（Enter）：不打断当前生成，本轮结束后按序自动发送」。
- ⚡（↑ 左侧次级小按钮，仅忙碌时可见）：tooltip「引导会话（Shift+Enter）：消息立即发出并登记进对话流，但不会中断当前生成」。
- 忙碌态 placeholder 切换为：「执行中：Enter 排队 · Shift+Enter 引导发出（不打断当前生成）」。

**推荐理由**：① 两个入口均可见、均可挂 tooltip，发现成本远低于长按，与 WorkBuddy「发送/引导」双按钮心智一致；② 不牺牲空闲态 Shift+Enter 换行，忙碌态复用为引导快捷键并以 placeholder 明示，无隐藏手势；③ 实现面小——两个 QPushButton + 现有 eventFilter 扩一个快捷键分支，不动现有发送链路。

## 5. 后端行为约定

### 5.1 排队消息存哪：服务端内存队列（推荐）

- 新增 `core/assistant/queue.py`：Assistant 单例持有 per-session `deque`（item = `{id, text, time, mode}`），锁保护；客户端通过 REST 变更、SSE 广播同步。
- **引导消息直到出队才写入会话 messages**（由 `start_turn` 现有逻辑落库），避免当前轮进行中插入用户消息打乱「用户消息 → assistant 回复」顺序。代价：未消费的引导消息刷新后从对话流消失（仅队列可见），列为已知限制（P2 落库解决）。
- 备选（不采用）：纯客户端内存队列——刷新即丢、多客户端不同步、不满足「登记在案」；备选（不采用）：入队即写 session——需处理与当前轮 assistant 回复的顺序问题，复杂且收益低。

### 5.2 本轮结束后如何触发下一轮：路由层循环消费（推荐）

- `routers/assistant.py` 的 SSE `gen()` 中，`start_turn` 返回后检查队列：非空则取下一条再次 `start_turn`，同一连接续推事件，直至队列空 / 暂停才发 `end` 与 `[DONE]`。
- 不采用 agent 内循环：`start_turn` 被单测与非流式路径共用，混入队列语义会破坏「一轮一职责」，且取消/错误语义更难收口。
- 出队顺序：**严格 FIFO**（按到达时间，含引导消息）。引导与排队的差异仅在「可见性 / 可改性」，不设优先权。

### 5.3 SSE 事件协议草案（在现有事件体系上扩展）

| 事件 | 字段 | 语义 |
|------|------|------|
| `queued` | `id, text, time, index` | 入队确认 |
| `queue` | `items[]` | 队列全量快照（任何变更 / 新轮次开始时广播，客户端以此为准重渲染） |
| `guided` | `id, text, time` | 引导消息已登记进对话流（客户端立即渲染用户气泡 + 时间） |
| `dequeued` | `id, text, mode` | 消息出队、即将作为下一轮处理 |
| `queue_state` | `paused, reason?` | 停止后 `paused=true`；恢复后 `false` |
| `end`（现有，语义收紧） | `content, error` | **仅当队列耗尽或暂停时**发出；客户端据此 `_end_streaming()` |

- 现有 `done` 仍表示「单轮答复完成」；中间轮次不再触发客户端结束忙碌态（这是 P0-2 的前端关键点）。
- REST 变更（编辑/删除/排序）经 HTTP 响应返回结果，同时向当前活跃流广播 `queue` 快照，保证其他监听端一致。

### 5.4 API 草案（REST）

- `POST /api/v1/assistant/chat`：body 增加 `mode`：`normal`（现状）/ `queue`（入队）/ `guided`（引导登记）/ `resume`（队列非空则出队头条开轮）；`stream` 语义不变。
- `GET /api/v1/assistant/queue?session_id=`：队列快照（重连恢复，P2 完善）。
- `PATCH /api/v1/assistant/queue/{id}` `{text}`：编辑（仅排队中可改；已出队/已引导返回错误）。
- `DELETE /api/v1/assistant/queue/{id}`：删除（引导消息不可删）。
- `POST /api/v1/assistant/queue/{id}/move` `{delta: -1 | +1}`：排序。

### 5.5 并发 / 取消语义

- 每会话同时最多一个轮次（沿用 `_running` / `_cancel` 保护）；所有队列操作加锁；编辑/删除遇到「已出队」竞态返回错误，客户端以 `queue` 快照为准刷新。
- **排队消息遇上用户点停止**：停止 = 取消当前轮（现有逻辑）+ 队列置**暂停**（`queue_state.paused=true`），**不出队**下一条；客户端在停止区 / 队列容器提供「继续」入口（POST `chat` `mode=resume`）。理由：不清空避免丢消息，不自动跑避免「停了还自顾自执行」的惊吓。
- 审批挂起期间：队列照常排队，不打断审批流程。
- 后端重启：内存队列丢失（已知限制）；重启后客户端按空队列处理，需重新输入。

## 6. 待确认问题（需用户拍板，附默认建议）

1. **停止时队列如何处理？** 默认：保留并暂停 + 一键「继续」（理由见 5.5）。备选：停止即清空队列。
2. **引导消息未消费时刷新页面会从对话流消失（仅队列可见），是否接受？** 默认接受（换实现简单、消息顺序正确；P2 落库解决）。备选：入队即写 session（顺序处理复杂）。
3. **交互方案确认：忙碌时 ↑=排队、次级 ⚡=引导、Shift+Enter=引导。** 默认推荐（理由见 4.2）。备选：长按 ↑=引导（发现性差、误触高）。
4. **队列长度上限？** 默认 20 条，超出提示「排队过多，建议等本轮结束再发」。备选：不设上限。
