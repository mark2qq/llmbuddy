## 1. WorkBuddy 的多任务并行执行流程（分析）

> 说明：WorkBuddy 是闭源桌面端，无法读源码。以下结论来自**本机可观察到的运行期行为**
> （工具调用记录、后台任务事件、子代理回执、`.workbuddy/` 目录结构），
> 属于行为级推断，标注了推断依据。

### 1.1 任务拆分与调度策略

| 环节 | WorkBuddy 的做法 | 观察依据 |
|---|---|---|
| 入口 | 用户一句话进「主理人」（lead agent），主理人**不直接开干**，先产出结构化任务清单 | 主理人回复里出现独立的「任务清单」条目，每条有标题、状态、依赖 |
| 拆分粒度 | 拆成**可独立验收**的子任务（不是按文件/按步骤机械切），拆到「彼此不依赖、可并行」为止 | 并行子代理的提示词里互相引用对方的产出，说明拆分时已做过依赖分析 |
| 调度 | 主理人维护任务清单，按依赖关系派发；无依赖的子任务**同时下发** | 同一轮内出现多个「已派发」记录，间隔很短 |
| 动态调整 | 子任务返回后主理人可追加/合并子任务（计划不是一次性冻结的） | 任务清单条目数在过程中变化过 |

**要点**：WorkBuddy 的并行是「主理人 + 子代理」两层结构，**拆分由模型做、调度由主理人做**；
子代理之间不共享模型上下文，因此并行度受限于「每个子代理都要重新建立上下文」的成本。

### 1.2 子任务 / 会话的创建与生命周期

- 每个子代理是**独立会话**：独立上下文窗口、独立工具权限、独立工作目录视图。
- 生命周期状态：`派发 → 运行中 → 完成 / 失败 / 被终止`。
- 运行中的子代理有独立的任务句柄（可轮询输出、可终止）；终止后句柄失效。
- 子代理的最终产出**以一段文本回执**的形式交回主理人，主理人不直接读子代理的中间过程。

### 1.3 并发控制与资源隔离

- 并发上限由调度器统一控制（不是无限开子代理）。
- 隔离体现在四个层面：
  1. **上下文隔离**：子代理看不到主理人的对话历史，只收到主理人显式下发的任务说明；
  2. **工具权限隔离**：只读子任务与可写子任务的授权面不同，高危动作仍需逐次批准；
  3. **文件系统隔离**：子任务写文件时限定在各自的工作目录，主理人最后统一归并；
  4. **进程/资源隔离**：子代理是独立执行单元，一个卡住不影响其它。
- 失败隔离：某个子任务失败不影响其它子任务继续。

### 1.4 结果聚合与回调机制

- 子任务完成即**回调**主理人（不是等全部结束再统一拉）。
- 主理人把多份回执**聚合成一份最终答复**（结论先行），并保留「哪个子任务给出了什么」的归属关系。
- 聚合是**显式动作**（主理人自己决定何时汇总），不是框架自动拼接。

### 1.5 失败重试与取消处理

- 重试由**调用方决定**：框架不自动重试（避免把「权限被拒」「参数非法」这类确定性错误重试一遍）。
- 取消是**协作式**：终止一个子代理时，它正在进行的工具调用/模型请求会在下一个检查点退出，已完成的部分保留。
- 取消与完成竞态时，**已完成的结果不会被回滚**。

### 1.6 上下文共享与状态同步

- WorkBuddy **不共享模型上下文**。跨子任务的状态靠三条通道：
  1. **文件系统**：`.workbuddy/memory/YYYY-MM-DD.md`（每日工作日志，追加写）+ `MEMORY.md`（长期结论）；
  2. **任务清单**：任务状态本身就是共享状态；
  3. **消息通道**：主理人 ↔ 子代理的显式消息。
- 状态最终一致：子代理写日志，主理人读日志，人看到的是同一份磁盘事实。

### 1.7 记忆功能：中断后如何从未完成节点续跑

这是 WorkBuddy 最值得抄的一点——**记忆落在磁盘，不落在上下文里**：

1. **写**：每完成一个可验证的节点就把进度追加进当日日志（append-only），
   内容包含「做了什么、得到什么、下一步该做什么」。
2. **读**：新会话启动时，先读当日日志 + 长期记忆，把「已完成 / 未完成」的清单重建出来。
3. **续跑**：未完成节点从日志里最后一条「下一步」接着做，已完成节点不重做。
4. **换模型照样能续**：因为进度在**文件**里，不在任何模型的上下文里——
   换一个模型只是换一个「执行者」，任务说明书（磁盘上的日志）没变，
   所以新模型读同一份日志就能接着干。
5. **代价**：日志是人可读的散文，不是结构化 checkpoint；
   优点是「模型自己就能读懂并接着写」，不需要专门的恢复协议。

> llmBuddy 的做法与它同源但更严格：把「日志」升级成**结构化断点**
> （子任务状态机 + 每个子任务自己的会话 id + 每次落盘），于是既能自动续跑，
> 又能在换模型后精确恢复到「哪个子任务的哪一步」，而不是靠模型读散文猜。

## 2. llmBuddy 实现方案概述

### 2.1 目标与取舍

| 目标 | 落地方式 |
|---|---|
| 并行执行多个子任务 | `ParallelRunner` + `ThreadPoolExecutor`，并发度受 `parallel_max_workers` 限制（默认 4，硬上限 8） |
| 复用既有抽象 | 子任务**走 `Assistant.start_turn`**（工具/审批/技能/上下文压缩/事件全复用）；拆分复用 `orchestrator.extract_json_array`；取消复用 `Assistant.stop()`；持久化复用 `parallel_store`（原子写 + RLock，同 `store.py` 约定） |
| 断点持久化 / 恢复 | `assistant/parallel/<plan_id>.json`：子任务状态机 + 每个子任务的 `session_id` + 各自当时的 provider/model |
| 跨会话续跑 | 断点文件与子任务会话文件分离：前者记「谁没干完」，后者记「聊到哪」；恢复时复用同一 `session_id`，模型能看到上次历史 |
| 跨模型续跑 | `resume(provider, model)` 只作用于**未完成**的子任务；已完成的结果与其模型记录原样保留 |
| 边界显式处理 | 超时（`subtask_timeout`）、重试上限（`parallel_max_retries`，只重试瞬时错误）、取消竞态（终态 cancelled 优先、已完成结果不回滚） |

### 2.2 状态机

```
plan:     planning ──run──▶ running ──┬─▶ done      （全部子任务成功）
                                     ├─▶ partial   （部分成功）
                                     ├─▶ failed    （全部失败）
                                     └─▶ cancelled （被取消，终态优先于其它）

subtask:  pending ──▶ running ──┬─▶ done
                               ├─▶ failed      （重试用尽 / 不可重试 / 超时）
                               └─▶ cancelled   （取消时尚未开工）
```

### 2.3 执行流程（一次 run）

1. `plan()`：模型把目标拆成 2~8 个子任务（严格 JSON 数组；拆不出来就降级成「单任务自己干」）；
   调用方已给定子任务时**不调模型**（确定性路径）。
2. `run()`：置 `running` → 落断点 → `ThreadPoolExecutor` 并发执行。
3. 每个子任务：先建独立 session 并**立刻落断点**（断电也知道对话落在哪个会话）→
   起独立 daemon 线程跑 `Assistant.start_turn` → 主控 `join(subtask_timeout)`。
   - 超时 → `Assistant.stop(session_id)` 协作式取消 → 标 `failed(timeout)`。
   - 失败 → 仅当错误属「瞬时类」（429/超时/网络/5xx）才重试，退避 `2.0×attempt`（封顶 6s）；
     「用户未批准」这类确定性错误**不重试**。
   - 每次尝试结束都更新断点。
4. `aggregate()`：模型汇总各子任务结论；模型不可用时**降级为拼接**（不编造，与
   `orchestrator` 的「不许编」红线一致）。
5. 落终态 + 写审计（`parallel_plan_created` / `parallel_plan_done` / `parallel_plan_cancelled`）。

### 2.4 取消与竞态

- `cancel(plan_id)`：置取消标志 → 对所有 `running` 子任务调 `Assistant.stop(session_id)`
  （复用 Agent 的协作式取消，provider 侧 `cancel_check` 在下一个分片退出）。
- 未开工的子任务：`running` 时检查到取消标志 → 直接标 `cancelled`，不执行。
- 已完成的结果**不回滚**（取消不回滚已完成工作）。
- 终态判定顺序：`cancelled` 优先于 `done/partial/failed`，避免「已取消」被改写成「已完成」。
- **取消后立刻续跑会撞「计划忙」**：原执行线程还在收尾（子任务线程退出中），
  此时 `resume` 返回 2032「计划还在收尾，请稍后再续跑」——这是显式的竞态处理，
  不是卡死；等收尾完再续跑即可。

### 2.5 断点续跑为什么能「接着上次聊」

- 断点文件记「哪个子任务没干完 + 它的 `session_id`」；子任务会话文件记「这段对话聊到哪」。
- 续跑时复用同一 `session_id` → `Agent.start_turn` 载入历史消息 → 模型看到上次的上下文，
  从**上次那个节点**接着做，而不是从头再来（真机验证：续跑后该子任务会话里
  `user/assistant` 三轮对话连贯保留）。
- `attempts` 跨续跑**累计**（审计可见「一共试了几次」）；单轮内的重试次数仍受
  `parallel_max_retries` 限制，续跑视为新一轮执行、给一份新的重试额度。

### 2.5 断点文件结构

```
assistant/parallel/<plan_id>.json
{
  "id": "p…", "goal": "...", "status": "running",
  "provider": "local", "model": "qwen3-4b",
  "max_workers": 4, "max_retries": 1, "subtask_timeout": 300,
  "subtasks": [
    {"id": "t1", "title": "…", "prompt": "…", "status": "done",
     "attempts": 1, "output": "…", "error": "", "session_id": "s…",
     "provider": "local", "model": "qwen3-4b",
     "started_at": 0, "finished_at": 0}
  ],
  "summary": "…", "events": [ … ]
}
```

- 原子写（`.tmp` + `os.replace`）+ 模块级 `RLock`：并发子任务同时更新也不会写坏。
- `events` 只保留最近 200 条（环形裁剪），避免文件无限膨胀。

### 2.6 配置项

| 键 | 默认 | 说明 |
|---|---|---|
| `parallel_max_workers` | 4 | 同时跑几个子任务（硬上限 8） |
| `parallel_max_retries` | 1 | 单个子任务最大重试次数（不含首次，上限 3） |
| `parallel_subtask_timeout` | 300 | 单个子任务时限（秒，上限 1800） |

三个键都必须写在 `store._default_config()` 里——`load_config()` 只回填默认里存在的键，
否则老 `config.json` 读不到（与 1.0.8 `tool_prefs` 同一个坑）。

## 3. REST 接口

| 方法 | 路径 | 说明 | 错误码 |
|---|---|---|---|
| GET | `/api/v1/assistant/parallel` | 计划摘要列表 | — |

业务错误一律 HTTP 200 + `fail(code, message)`（与既有接口一致）。

### 4.1 附带修复：冻结包模态对话框崩溃（0x8001010d）

装机验证时复现到一条**与本模块无关、但会毁掉整轮验收**的崩溃：

    Windows fatal exception: code 0x8001010d
    当前线程：main.py → QMessageBox.exec()（模态弹窗）
    另有一个工作线程：httpx socket.connect（探测后端）

`0x8001010d` = RPC_E_CALL_REJECTED「调用被拒绝」，是**瞬时**错误（Windows OLE 消息
过滤器的标准做法就是让调用方稍后重试），但 Windows 默认「未处理异常 → 终止进程」，
于是弹个窗就把进程带走。触发条件：**模态对话框 + 其它线程正在做 socket/httpx**，
典型场景就是「后端没启动时启动客户端」→ 弹「启动本地服务」。

| 文件 | 关键改动 |
|---|---|
| `client/core/dialog_guard.py`（新增） | 启动时把 `QMessageBox.question/information/warning/critical` 与 `QColorDialog.getColor` 换成「实例 + `DontUseNativeDialog` + `exec()`」，一处生效、全局覆盖 40 多处调用点（PySide6 里 `Option` 与 `StandardButton` 不能直接 OR，只能走实例 + `setOption`） |
| `client/core/win_exception_guard.py`（新增） | 注册 Windows 向量异常处理器，**只**对 0x8001010d 返回 `EXCEPTION_CONTINUE_EXECUTION`（放行重试），其余异常码一律交回系统（不会被吞掉）；非 Windows 平台安全跳过 |
| `client/main.py` | 在建窗口前安装上面两个守卫 |
| `client/ui_tests/test_dialog_guard.py`、`test_win_exception_guard.py`（新增） | 7 个用例 |

装机复验：22:15 那次「后端未运行」启动 **不再产生新转储，进程存活、弹窗正常**。

客户端 `ui_tests` **383 passed**（新增 7 例为对话框/异常守卫）。

真机端到端验证（本地引擎 + 硅基流动真实模型）：

| 验证点 | 结果 |
|---|---|
| 拆分 → 并行执行 | 两个子任务各自独立会话并行跑，t1 产出真实结论、t2 产出真实摘要 |
| 聚合 | 计划终态 `done`，summary 为模型汇总的真实报告 |
| 取消 | `/cancel` 立即生效，终态 `cancelled`，已完成结果保留 |
| 断点续跑 | 把 t2 置为中断态后 `/resume`：**t1 结果未被重跑**、t2 复用**同一 session_id** 续跑（该会话文件里 user/assistant 三轮连贯），attempts 累计 |
| resume 时机 | 取消后立刻 resume 返回 2032「计划还在收尾」——显式竞态处理，等收尾后再续即可 |

# 附录 A · 1.0.10 增量：工作空间内多任务并行 + 思考/执行严格串行

> 需求来源（2026-10-27）：
> 1. 同一工作空间允许同时创建、运行多个任务；新任务不得覆盖、复用或中断旧任务；
> 2. 任务与空间关联、任务 ID 生成、运行状态独立保存与查询要说清楚；
> 3. 流式输出里「思考区」与「执行区」必须分组、排序；
> 4. 后端执行严格串行：**思考 → 执行 → 如有问题再思考 → 再执行**，不得思考与工具/技能调用同时发生。

## A.1 两个「并行」不是一回事（先分清）

| 维度 | 1.0.9 的并行（`parallel.py`） | 1.0.10 的并行（本次） |
|---|---|---|
| 谁在并行 | **一个任务内部**的多个子任务（模型拆分 → 并发子会话 → 聚合） | **多个任务**（同一工作空间下的多条对话）同时跑 |
| 会话单位 | 每个子任务一个 `session_id` | 每个任务一个 `session_id`（本来就是） |
| 用户看到什么 | 一条对话流里出现「已拆分 N 个子任务」 | 左栏多个任务行同时带 ● 运行标记，各自独立的对话区 |
| 关键约束 | 子任务之间上下文隔离、失败隔离 | 任务之间**运行态完全隔离**：新建/切换/停止一个任务不影响另一个 |

## A.2 客户端运行态：每任务一个 `TaskRun`

页面原来把运行态挂在页面级字段上（`_stream` / `_busy` / `_bubble` / `_thinking` /
`_proc` / `_approvals` / 队列 …）。只要页面「只有一个」，切任务就等于把另一个任务的
状态顶掉。1.0.10 把这些字段整体搬进 `TaskRun`：

| 分组 | 字段 | 作用 |
|---|---|---|
| 运行态 | `stream` / `busy` / `status` / `error` / `phase` / `round` / `gen` | 该任务自己的 SSE 流与阶段；`gen` 是流代次，旧流的迟到事件直接丢 |
| 界面 | `container` / `col` / `layout` / `bubble` / `thinking` / `proc` / `approvals` / `follow` / `scroll_pos` | 每个任务**一整块独立对话容器**，切任务只是把容器换到 `QScrollArea` 上 |
| 队列 | `q_items` / `q_paused` / `q_seq` | 引导会话队列按任务各存一份，快照乱序只作废自己那份 |

页面上的 `self._stream` / `self._bubble` / `self._busy` / `self._queue_items` …
全部改成**属性**，读写都落到「当前上下文任务」（`_cur_sid`）的 `TaskRun`。
`self._session_id` 同样是属性别名（= `_active_sid`），
赋值即「切到那个任务」，保证「显示的任务」与「当前会话 id」永不脱节。

三个身份要分清：

| 字段 | 含义 | 谁改 |
|---|---|---|
| `_runs[sid]` | 任务运行态登记表（含后台任务） | 新建 / 切换 / 删除任务 |
| `_active_sid` | 当前**显示**在页面上的任务 | `_show_run()` |
| `_cur_sid` | 当前**事件处理上下文**（后台任务事件处理时临时切） | `_using()` 上下文管理器 |

事件路由因此不再是页面级的 `self._on_event`，而是带 sid + 代次的闭包：

```
stream.event    → _on_run_event(sid, gen, ev)   # gen 不符 → 丢弃
stream.failed   → _on_run_failed(sid, gen, msg)
stream.closed   → _on_run_closed(sid, gen)
```

`_on_run_event` 用 `with self._using(sid)` 把 `_cur_sid` 临时切到该任务：
内容写进**它自己的容器**，状态栏 / 滚动条（只有一份，属于可见任务）不动。

## A.3 任务 ID、空间关联、运行状态

| 关注点 | 实现 |
|---|---|
| 任务 ID | 后端 `Agent.new_session()` 生成 `s` + `uuid4().hex[:12]`，全局唯一；客户端并发创建不会撞号 |
| 与空间关联 | 任务落库即带 `workspace`（`norm_workspace` 归一化后的绝对路径）；左栏「空间」区按这个字段分组；新建时 `+` → 系统默认工作区，空间右键 → 该空间 |
| 运行状态保存 | 后端 `Assistant._running`（sid → bool）是权威值；`state.running` 与 `GET /sessions` 每行的 `running` 都从这里派生 |
| 运行状态查询 | 客户端 `TaskRun.busy`（本地流）**或** 后端 `running`（跨窗口/重启后仍准）→ 左栏行首 ● |
| 防重复创建 | 客户端 `_claim_create(ws_key)`：同一工作区 20s 内只允许一个在途创建请求，失败/成功都立刻释放名额 |

新建任务时**绝不复用**正在跑的任务：`_new_session()` 的「空任务直接复用」分支新增
`not self._busy` 条件；同 id 的任务只在**它正在跑**时才接管（重试/重放），
否则视为新任务、旧缓存作废。

并发上限 `MAX_PARALLEL_RUNS = 4`（同时运行的流）。到顶后 `_on_send_clicked`
**不发流也不吞消息**：状态栏提示、输入框内容保留。

## A.4 思考 / 执行分组与排序（前端）

修的是一个真实错位：旧实现整条流只建**一个** `ThinkingBlock`，第二轮（工具执行之后）
的思考会追加到**最上面**那块里 —— 用户看到「思考 → 执行 → 思考还在上面长」，
主观感受就是「思考和执行同时在跑」。

现在的规则：

| 阶段 | 触发 | 渲染动作 |
|---|---|---|
| 思考开始 | `phase=thinking` | 封口执行行（下一次工具调用另起一行），思考块下一段另起一块 |
| 思考流 | `reasoning` | 当前思考块 append（没有就新建并追加到消息末尾） |
| 执行开始 | `phase=executing` / 首个 `tool_call` | 本轮过渡气泡定稿（`_finish_bubble`）、思考块封口、`proc=None` |
| 执行流 | `tool_call` / `tool_result` / `skill_step` | 并入当前 `ProcessLine`（同一批并行调用合并成一行摘要） |
| 回答 | `delta` | `_ensure_bubble()` 新建气泡，天然排在执行行之后 |

于是顺序恒为：**思考块(第1轮) → 执行行(第1轮) → 思考块(第2轮) → 执行行(第2轮) → 回答**。
老后端没有 `phase` 事件时按「`tool_call` = 执行开始」推断，分组行为一致。

## A.5 后端严格串行：`PhaseGate`

`core/assistant/turn_phase.py` 给 `emit` 套一道闸门：

| 方法 | 行为 |
|---|---|
| `emit(ev)` | 思考阶段直通；**执行阶段**到达的 `delta` / `reasoning` 先缓存，不放行；外部伪造的 `phase` 事件直接丢 |
| `enter_executing(round)` | 先补发缓存（正常为空）→ 再发 `{"type":"phase","phase":"executing","round":n}` |
| `enter_thinking(round)` | 先补发缓存（保序）→ 再发 `{"type":"phase","phase":"thinking","round":n}` |
| `flush()` | 轮次收尾补发，保证一个 token 不丢 |

`Agent.start_turn` 的接入点：

```
每轮开始（provider.chat 之前）  → gate.enter_thinking(rounds)
一批工具执行之前                → gate.enter_executing(rounds)
finally（轮次收尾）             → gate.flush()
```

为什么需要闸门而不是「反正 agent 是顺序的」：异步流式实现可能在 `chat()` 返回后
继续把尾巴 token 推给 `on_delta`，而工具已经在跑 —— 那就是「思考与执行同时发生」。
闸门让这类事件**推迟到执行结束之后**再发，宁可晚一点显示，也不交叉。

## A.6 测试与验证

| 层 | 用例 | 断言要点 |
|---|---|---|
| 闸门单测 | 思考直通 / 执行缓存 / 切回补发保序 / 外部 phase 被丢 / flush 不丢内容 / round 递增 | 事件序列精确匹配 |
| Agent 集成 | 两轮工具调用 | `phase` 序列 = `(thinking,1) (executing,1) (thinking,2)`；执行阶段的窗口里没有 `reasoning`/`delta` |
| 异步尾巴 | provider 在执行中继续推 token | 顺序 = 执行开始 → 工具返回 →（补发）迟到思考 → 下一轮思考 |
| 客户端并行 | 新建任务不动旧任务 / 切回来接着看直播 / 忙碌态按任务算 / 并行上限 / 连点防重 / 创建失败释放名额 / 单独停后台任务 / 队列按任务隔离 | 旧任务的流与内容原样；事件不串台；名额可重试 |
| 客户端分组 | phase 分组 / 无 phase 兼容 / 两轮执行两行进程 | 控件类型顺序 = `think, proc, think, bubble`；两块思考文本互不污染 |
