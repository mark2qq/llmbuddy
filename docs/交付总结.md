## qwen3 思考模式联调（WorkBuddy 接入）
**现象**：WorkBuddy 等只读 `message.content` 的客户端显示空回复——qwen3-4b 默认思考模式，正文全部进入 `reasoning_content`。

**排查结论**：该 GGUF 内置模板硬编码思考（`assistant\n<think>\n`，无 `enable_thinking` 分支）。实测**无效**的手段：`/no_think` 软开关、请求级/服务端 `chat_template_kwargs enable_thinking=false`、引擎 `--reasoning off`、`--reasoning-budget 0`、自定义模板（去 think 标签/空思考块，均致输出乱码）。**思考无法关闭**；但引擎默认模板 + 足够 max_tokens（≥1024）时，思考进 `reasoning_content`、正式回答正常进 `content`。

**修复（网关层兜底，不动引擎行为）**：
- `routers/gateway.py` `_normalize`：非流式 content 为空但 reasoning_content 有值 → 回填；
- `routers/gateway.py` `_rewrite_sse_line`：流式把 `delta.reasoning_content` 合并进 `delta.content`（保留 reasoning 字段）；
- `core/pool.py`：`REASONING` 默认 `off` → `auto`（off 无效，auto 下引擎 reasoning/content 分流正常）。

**端到端验证 PASS**：加载 6s 就绪；非流式返回干净回答（"你好！我是通义千问，一个能回答问题、创作文字、编程的超大规模语言模型。"）；流式 TTFT 0.39s、思考+回答完整可见。

**WorkBuddy 接入配置**：Base URL `http://127.0.0.1:8000/v1`、模型名 `qwen3-4b`、API Key 不设（`LLM_API_KEY` 为空则开放）；`max_tokens` 建议 ≥1024、请求超时 ≥120s（CPU 推理 + 4B 思考耗时，非流式全量约 40~60s）。

## 已知限制 / 后续建议
1. 客户端 GUI 交互未在有显示环境实跑联调（headless 限制），建议首次在 Windows 上运行核对布局与流式对话效果。
2. GitHub 目录默认用内置 curated 清单（离线可用）；如需联网全量目录可配置 `LLM_CATALOG_URL`。
3. 模型下载源默认可指向 HuggingFace 直链（大模型常 >2GB）；本机无 NVIDIA 时走 CPU 推理。
4. 无头后台常驻（Windows 服务/开机自启）为可选增强，首版用「GUI 托盘常驻」满足守护诉求。
5. 测试的清理逻辑会按进程名结束 `llama-server.exe`，本机 Ollama 自带的引擎会被顺带结束（Ollama 下次请求会自动重启，无实际影响）；如需更精细可按 PID/父进程过滤。
